# CRM 多端协作约定

本文件适用于 `projects/crm/`。通用流程、文档写作和 Git 授权边界遵循[工作区约定](../../AGENTS.md)，接入状态见 [README.md](README.md)。

- 本项目已确认接入 iOS、Android 两个端，后续可能增加第三端；代码仓库见 [repos/README.md](repos/README.md)，所属部门和业务范围尚未确认，不从云诊室项目推导。
- 代码仓库放在 `repos/` 下，各自保留独立 Git 历史。接入后先读目标仓库现行 AGENTS、README 与必要规范，不继承云诊室的技术架构、分支命名或发布流程。
- 开始需求先确定实际版本、本人负责范围、适用端和目标仓库；按已接入且本次适用的端核对业务，不为未来第三端创建当前任务或验收要求。
- 版本资料放在 `prd/prd-vxxx-YYYYMMDD/<姓名>/`，当前用户为 `sanshi`。同一版本复用首次创建日期，入口登记在 [prd/README.md](prd/README.md)；尚未确认版本时不创建假定版本目录。
- 共用模板引用[工作区模板说明](../../docs/requirements/README.md)，按实际平台裁剪。
- 本项目协作文档由工作区根仓库统一做本地版本记录，不另建文档仓库、不上传远程；代码 commit、push、amend 需用户明确授权并遵循所属仓库规范。
- 发布记录待收到已确认的平台和发布信息后在本目录按端建立，只记录版本号、发布日期和简短业务条目；不复制云诊室历史，不从计划或分支推定发布事实。

## 多端需求与技术方案

- **共用一份产品开发需求。** 同一版本、同一负责范围内，iOS 和 Android 共用一份产品开发需求文档。两端共用的功能统一定义业务流程、规则、状态含义和验收标准。
- **在需求条目中标明平台差异。** 涉及单端范围，或两端业务行为、用户可见交互不同的，在对应需求条目写明适用端、各端预期表现和对应验收标准。差异由用户确认后纳入需求。
- **按端分别编写技术方案。** iOS 和 Android 分别为本次涉及的功能维护技术方案，引用共用需求中的需求编号（REQ）和验收标准编号（AC）。在满足已确认的业务规则及各端验收标准的前提下，代码组织、组件和实现方式按本端项目结构与规范确定。

## 需求开发流程

1. **接收产品需求和设计。** 产品提供基础需求、业务目标和原始说明，UI 设计提供对应设计稿和交互说明。记录需求与设计的版本或来源，便于后续确认和追踪变更。

2. **确认开发基线，整理共用需求列表。** 先确认目标版本、本人负责范围、适用端，以及各端从哪个分支开发、合到哪里。结合产品需求、设计稿和本次涉及的现有代码，整理一份 iOS、Android 共用的产品开发需求。逐项写清目标、入口、业务规则、本期范围、必须保留的行为和验收标准，按可独立开发和验证的功能模块拆分。单端需求或用户可见差异写在对应需求条目里，标明适用端、各端预期表现和验收标准。

3. **确认需求和设计。** 将需求列表提交你确认。无异议时可一次通过。有异议时，列出具体场景、两端现状和影响，由产品确认业务规则、UI 设计确认交互表现。修订需求或设计后，只对受影响的条目重新确认，其他已确认的模块可以继续推进。

4. **编写各端技术方案，准备联调和测试。**
   - **技术方案与开发任务。** iOS、Android 分别写技术方案，引用共用需求的需求编号（REQ）和验收标准编号（AC）。业务规则与验收口径按共用需求执行，代码结构和实现方式遵循本端规范。各端任务写清改动范围、依赖和完成条件，小改动用简表即可。
   - **历史差异与联调条件。** 只核对本次涉及的历史差异。简单差异记在共用需求里，涉及多个入口、状态或历史数据时，单独写差异文档并链接到对应需求。新增且影响业务或交互的差异按第 3 步确认保留还是对齐。同时确认接口、开关、测试环境、账号角色、测试数据和设备条件，记录阻塞范围和负责人。iOS 涉及 GAPI 时安排真机验证。
   - **自动化与人工用例。** 按端为每条适用的验收标准安排验证方式。AI／自动化用例记录可执行条件、检查项和证据。人工测试验收文档集中写明改动范围、受影响的场景和参考用例，包含入口、操作步骤和预期结果。测试人员可在这一步核对用例和测试准备条件。

5. **实现功能并完成开发侧验证。** 按已确认的需求、各端技术方案和 UI 设计实现功能，执行约定的开发自测、自动化验证和必要回归。按端记录构建、环境、结果和证据。受设备、账号或数据限制的场景，标明阻塞原因和后续验证安排。

6. **提供可运行构建，请你手动复核。** 开发侧验证完成后，提供各适用端可运行的构建，标明版本、环境和账号角色。从人工测试用例中挑出关键主流程、平台差异和受影响的历史行为，列明入口、操作步骤和预期结果，供你复核。修复复核发现的问题后，提供对应构建并复核受影响场景。

7. **正式提测，跟进缺陷复测和验收。** 你复核确认后，向测试人员交付各端安装包、构建与环境信息、提测范围、参考用例和已知限制。复核用构建符合提测要求时可直接复用。若正式提测包更换了签名或配置，补测安装和受影响的主流程，涉及升级时核对覆盖安装。提测后，开发修复缺陷并提供新构建，测试人员复测并记录各端结论、遗留问题和未验证范围，产品按职责记录业务验收结论。

## 开发与交付

以下 N01–N07 已于 2026-11-05 经用户确认，适用于 CRM 项目；来源与项目现状见[项目描述](项目描述.md)。各端具体架构、组件和工程操作继续遵循本端规范。

- **N01 分支与规范核对**：每次任务先确认目标仓库、实际分支和目标目录规范。项目说明中的分支、配置和验证信息仅作为带日期快照；当前检出缺少规范时，先核对目标分支，不把“未看到”直接当作“没有”。
- **N02 公共改动影响**：修改公共基类、共享组件和全局工具前，先确定受影响页面；只为单个页面服务的行为，优先局部处理。
- **N03 兼容性与历史行为**：修改接口字段、缓存键、通知、路由、模型及状态处理时，先沿现有调用链核对兼容影响；未明确改变的历史兜底和必要行为继续保留。
- **N04 复用与适度抽象**：新功能复用目标模块当前的网络、组件和状态处理方式；只有业务复杂度确有需要时再增加抽象，不为单个简单页面引入整套新架构。
- **N05 验证与交付状态**：交付分别说明代码实现、构建／静态检查、设备／接口验证的实际完成情况，列出未验证原因和剩余事项；代码完成不能自动记为业务验收完成。按风险选择必要验证，不机械补齐全量测试。
- **N06 发布影响与产物**：修改依赖版本、构建、签名、打包脚本、SDK 初始化或环境配置时，单独说明发布影响和验证范围；发布包保留对应符号／混淆映射，分发前核对实际包身份。
- **N07 跨端差异与优化确认**：仅在开发当前需求、核对相关入口和调用链时，对实际发现的 iOS、Android 逻辑差异及优化、对齐机会，列出两端现状、依据、影响和建议。日常不单独扫描或寻找差异、优化点，不为整理清单扩展排查范围；用户另行要求专项分析时按指定范围执行。默认只记录并向用户提出，不顺手优化或统一实现，不自行选某端作为标准；保留已确认的平台差异。与用户讨论并确认具体调整范围后再修改，同步相关需求、方案和验收资料。待确认事项只暂缓受影响部分，其他已明确授权的需求内容继续推进；常规实现细节按现有授权和本端规范处理，不扩大本次需求范围。
