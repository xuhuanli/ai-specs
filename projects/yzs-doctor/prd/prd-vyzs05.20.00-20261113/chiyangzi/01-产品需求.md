## 背景、目标与责任边界

医生在开方后、回看订单和浏览患者病历时，将选定病历与药方正式存入个人云医案，并独立设置当前患者的后续新诊次是否自动同步。新入口直接入案；原批量导入仍保留待审核入组流程。

本次 App 范围包括三个入口、共用存入弹窗、接收患者核对、诊次选择与预览、本诊图片展示、后续同步开关、结果与重试交互，以及 H5／云医案小程序跳转和返回恢复。云医案患者与诊次页面作为跳转目标和联调依据，不属于三端 App 需要重新实现的页面。

服务端的账号归属、患者关联、逐订单入案、附件识别与归类、自动同步任务、旧待审核池处理属于外部依赖。App 需要展示和消费其结果，本轮不将这些能力写成客户端本地实现。PDF 自第 27 页「开方页 AI 建议首次生成与病历更新优化」起的内容不在本次范围。

## 角色、数据与主流程

- 操作者为当前登录医生，处理本人名下当前就诊人的正式药方订单；咨询记录、问诊单原始回答与模型推断不能直接当作医生已确认病历入案。
- 源就诊人、云医案接收患者与订单对应诊次分别有身份关系。姓名、性别和年龄用于核对，不代替双方 ID 关系。
- 一个药方订单对应一个诊次；同一天多笔订单分别处理。手动存入不要求订单已支付，手动可选历史不受旧批量近一年范围限制。

主流程：进入来源页面 → 检查开通状态 → 核对接收患者 → 选择并预览诊次 → 确认存入 → 展示结果 → 查看对应医案或返回来源。已有有效患者关联时，后续同步开关可独立保存。未开通时经过介绍与开通流程，返回后继续原任务，不直接提交存入。

## 业务与交互需求

### REQ-001 三个入口与患者同步状态

来源：PDF 第 2—6、19—20 页；Demo N01、N06、N03；Figma 页面入口。

1. 开方完成页、开方记录详情页提供存入入口；当前订单已存时提供「查看云医案」，按该订单实际对应的目标查看。
2. 患者档案展示未存入、部分存入、全部存入、关联失效、无可存药方等状态。计数只统计当前范围内可存的云诊室药方订单；有新诊次未存时不再算全部存入。
3. 全部已存时可查看记录和调整后续开关，已存诊次不能再次勾选。只有咨询或问诊单时显示「暂无可存入的药方订单」，关闭空态不创建空患者。
4. 患者档案采用 Figma 中位于「患者病历」标题上方的入口卡片：未开通展示「去开通」，已开通展示「我的云医案」、存入数量／状态与后续同步开关摘要。各状态文案对应设计节点，Q-001 已确认；刷新时机仍见 Q-005。

### REQ-002 共用弹窗、选择与预览

来源：PDF 第 7—8、11—12 页；Demo 三入口；Figma 弹窗及注释。

- 开方完成或详情进入，默认仅选中来源订单并标记当前诊次，可追加其他待存诊次。从历史订单进入时需定位该记录；不得默认替用户存入全部历史。
- 患者档案进入，默认选中全部待存诊次，不显示当前诊次标签。待存记录按时间倒序展示；全选仅影响待存记录，已存记录只读。
- 一旦有已存诊次，弹窗显示「待存入诊次」与「已存入诊次」两个 Tab 及数量；部分存入默认待存 Tab，全部存入默认已存 Tab。尚未存入任何诊次时采用 Figma 首次存入列表。
- 点击诊次「详情」进入二级详情弹窗，返回时保留主列表选择与位置。待存诊次支持在详情中明确选择／反选，并同步主列表和确认数量；已存诊次详情只读。单纯打开或关闭预览不改变选择，没有可提交诊次时不发起存入。
- 二级详情按 Figma 展示患者信息、药方信息，包含主诉、诊断、处方与源订单实际已有的病历信息；服用方式、医嘱在详情中按稿展示。详情字段空值沿用源页面的未填写或隐藏处理。
- Figma 的诊次详情还提供患者信息、药方信息分区复制及「复制成功」反馈；复制字段与文本格式见 Q-013。
- Tab、诊次摘要卡片和二级详情弹窗按 Figma 实现，Q-001 已确认。未勾选时按钮禁用与点击提示的设计内部歧义仍见 Q-007。

### REQ-003 核对云医案接收患者

来源：PDF 第 9 页；Demo N01、N06；Figma 同名患者弹窗。

已有有效关联时展示该接收患者。没有候选时提示将新建当前患者并归入默认分组；有候选时展示姓名、性别、年龄、云医案分组和已有诊疗数量，医生明确选择后再提交，候选不自动勾选。不是同一人时可选择新建患者。

用户已确认按 Figma 注释，仅展示同名且同性别的候选，Q-002 已确认；不采用 PDF 中把其他性别也列入候选的分级展示。姓名沿用去除首尾空格后完全相同的比较；默认只显示第一位匹配候选，超过一位时提供「展开全部同名患者」，展开后仍只包含符合筛选条件的候选，均不自动选中。设计例中的不同性别资料不作为筛选依据。

候选排序、字段缺失等设计未说明的边界见 Q-014，不重新讨论已确认的同名同性别范围。有效关联的主动更换权限与历史关系范围见 Q-003；Demo 中的「更改」不直接作为新增入口依据。

### REQ-004 关联失效与获取失败

来源：PDF 第 9—10、25 页。

云医案整个患者被删除后，提示「患者关联已变更，请重新选择」，进入重新选择或新建流程，再由医生选择需要存入的诊次。失效关联不能继续计为有效已同步，重新存入按云诊室仍保留的资料处理。

患者信息暂时查询失败时保留当前选择并提供重试，不能把查询失败判定为无同名患者，也不能据此自动新建。重关联不自动将后续同步改为开启；已存订单的原目标关系与重新关联的范围由服务端确认。

### REQ-005 预览及同步内容

来源：PDF 第 12—14 页。下表为业务映射，接口字段与客户端、服务端分工在联调时核对。

| 源资料 | 目标与规则 |
| --- | --- |
| 姓名、性别、年龄 | 新建时带入并用于身份核对，不覆盖已有患者档案 |
| 开方时间 | 就诊时间，使用订单成功开具时间 |
| 主诉、现病史、刻下症 | 保留医生确认的原始内容；普通开方不遗漏刻下症，源订单无字段时不补造 |
| 诊断 | 沿用旧批量同步的疾病／证候归属；具体拆分待旧规则与协议核对 |
| 既往史、过敏史 | 首次新建时带入；已有患者仅在接收字段为空时补齐 |
| 药材、剂量、单位、炮制、剂型／煎服方式、剂数 | 按原方保存；逐味展示药材名和剂量，有炮规时保留炮规，末尾保留煎服方式及剂数；不增加通用方名。多炮规与完整格式见 Q-010 |
| 医嘱 | 保留医生确认的原文与单位 |
| 用药反馈 | 存入时已有内容进入复诊反馈，之后不自动补推 |

附件仅处理所选诊次的本诊图片。图像类型识别与归类为同步服务依赖：舌象、面照、患处照片进入体格检查附件；检验／化验单、影像报告、处方单或药方原图、病历与其他医疗文档进入辅助检查附件；药品实物、包装、医疗聊天截图与非医疗图片进入备注附件。附件规则也影响旧批量同步，App 不自行推断图片类型。

云医案侧编辑不回写云诊室。预览、提交和接收内容需关联同一来源订单；PDF 右侧被裁切的文字与未读取的旧 PRD 见 Q-010。

### REQ-006 本诊图片展示

来源：PDF 第 14—16 页。

本诊图片指同一医生、同一就诊人的本次已完成开方相较上次已完成开方，新增且随本订单保存的诊疗图片。第一次开方保存的图片均属本诊；沿用历史图片不重复算新增；没有新增则本诊数量为零。识别依据需由订单或附件协议提供，不能按当前列表位置猜测。

开方记录附件区增加「仅看本诊」，切换仅改变展示范围，本诊图片带「本诊」角标；无本诊图片时不显示筛选入口。大图预览展示当前图片上传时间，切换图片同步更新；历史图片缺失时间时隐藏该项。筛选关闭、默认状态及完整稿见 Q-012。

### REQ-007 后续医案自动同步

来源：PDF 第 17、26—27 页；Figma 帮助提示与开关。

| 场景 | 设置生效与范围 |
| --- | --- |
| 已有有效患者关联 | 调整开关独立保存，无需再次确认存入；失败时反馈并与服务端真实状态一致，不能显示成已保存 |
| 首次存入 | 默认开启；接收患者与开关先作为本次选择，确认存入成功后保存 |
| 关联失效后重新关联 | 不自动重置为开启，提交成功后保存本次确认结果 |
| 首次开启或重新开启 | 从本次设置生效起算新订单范围；持续开启不重置起点 |
| 自动入案触发 | 订单须在本次开启后新建，且支付成功时开关仍开启；未付可手动存入 |
| 关闭、重开与退款 | 不补存开启前或关闭期间新建的历史订单；已触发任务继续完成、失败可重试；退款不撤回已存资料 |

补存历史不改开关。首次默认与已有关闭状态需区分；Figma 对开方入口默认开关的注释见设计差异，不能无条件覆盖已保存设置。部分成功时关联与开关如何提交见联调依赖 DEP-003、DEP-004。

### REQ-008 存入结果、重试与去重

来源：PDF 第 18、27 页；Figma 处理中、成功与失败稿。

只提交当前所选待存诊次。提交期间防止重复操作；存在有效已存关系时，其他入口不得再次创建同一来源订单对应的诊次。确认整个目标患者已删除后的重新存入，按 REQ-004 处理；仅删除一个目标诊次不开放重新存入。

| 结果 | 用户可见处理 |
| --- | --- |
| 全部成功 | 展示本次已存数量与接收患者，可查看云医案或返回来源并更新状态 |
| 部分成功 | 分别展示成功、未存入数量；重试只处理未存入诊次，保留成功结果；支持稍后处理 |
| 结果未知／请求超时 | 先查询实际结果，再处理尚未完成项；不能将整批重新创建或清除已成功结果 |
| 明确失败 | 展示可理解的失败反馈并允许安全重试；Figma 的错误代码与失败后操作见 Q-009 |
| 服务端处理中 | Figma 展示「正在存入我的云医案…」并允许离开后查看；是否异步、如何恢复与查询由 DEP-003 确认 |

PDF 后续事项明确部分成功交互已确定但结果图待补；能否出现逐诊次部分成功及其返回形式仍需联调确认。本次尚未定位部分成功和结果未知的专用 Figma 稿，不能省略对应处理。

### REQ-009 未开通时继续原任务

来源：PDF 第 21—24 页；Figma 介绍页、返回确认框与注释。

仅未开通医生先进入 H5 介绍，通过「一键开通云医案」完成开通并进入微信小程序现有首页。按 Figma，返回 App 后先弹「请确认您是否已完成开通？」，提供「取消」「我已开通」；点击「我已开通」再查询真实开通结果。确认已开通后恢复来源患者、订单、入口和所选诊次，进入存入弹窗继续确认；未开通时仍保留开通路径。取消仅关闭确认框、保留原任务，不提交存入。Q-004 先前暂缓的状态已被用户后续「交互以 Figma 为准」的决定更新。

返回后保留原页面滚动位置与返回路径，不直接提交入案。开通失败按 Figma 提示「开通失败」并保留原操作上下文，后续可重试；查询失败不能被写成已开通或确定未开通，其协议与异常细节见 DEP-005。App 进程退出后是否恢复未提交选择见 Q-006。H5 中近 12 个月批量同步宣传与本次单患者入口边界见 Q-008。

### REQ-010 查看患者与对应诊次

来源：PDF 第 25—26 页；Demo 模拟查看。

患者档案的存入／查看入口打开实际接收的云医案患者档案；订单详情及某条已存记录打开该订单保存时对应的患者与诊次，不能只按当前患者关联跳转。

目标诊次被删除而患者仍在时，订单仍计已存，不重新开放勾选或自动补建；查看时回退同一患者最新诊次，若无诊次则打开患者档案。整个患者被删除时进入 REQ-004，不跳转另一位同名患者。小程序页面、参数、权限与三端唤起方式待 DEP-005 确认。

### REQ-011 旧批量流程与数据隔离

来源：PDF 第 26—27 页。

新入口直接入案，不再送到旧待审核池。任一入口成功后，仅移出待审核池中对应诊次；其他资料保留，全部存入后该患者才退出待审核列表。同一订单跨入口、重试和自动同步只入案一次。

旧审核入组与新入口共用该患者的后续同步设置。原已审核患者沿用开启，医生后来关闭的除外；分组调整、全局批量导入、后台同步与重试不改患者开关。旧批量近一年、每日增量的范围继续由原流程负责；单患者开通或存入不触发全局批量导入。

切换来源患者、订单或登录医生时，待选诊次、候选患者与结果应保持各自归属，不把上一对象的选择用于当前对象。历史已存关系的准确性需以服务端结果为准。

## 三端共同要求与允许差异

三端共用上述业务含义与 AC，不要求相同代码结构。系统返回方式、窗口尺寸、安全区和微信唤起能力按本端处理；允许变化的具体交互尚未确认，不将 Figma 的 375×812 画板直接作为三端固定屏幕尺寸。

本轮只读核对到少量现有入口与资源，尚未完成受影响调用链、接口或三端同场景行为比较；未核实端间差异不据此判定功能不存在。实施前的现状核对安排见任务清单。
