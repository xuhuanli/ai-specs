# 产品需求与配套文档使用说明

本目录提供跨业务项目共用的五份配套模板。使用前先确定项目标识、需求版本、本人负责范围和实际适用端；两个端的项目按两个端处理，不为未来平台创建当前任务或验收要求。产品需求统一多端的业务逻辑和交互，开发和测试在此基础上分别维护实现方案、任务和测试资料。每份文档都有明确的负责人，相关人员可以参与补充，由负责该事项的人确认结论。

版本资料按版本和文档负责人归档，路径为 `projects/<项目标识>/prd/prd-vxxx-YYYYMMDD/<姓名>/`。当前用户的目录名为 `sanshi`，默认只在对应版本的 `sanshi/` 下生成本人负责需求的文档，不自动覆盖整版需求。资料由根目录文档仓库记录本地提交，不上传任何远程，也不加入多端代码仓库。目录和 Git 边界见[根目录 README](../../README.md)。

## 1 五份文档与填写职责

| 文档 | 主责填写 | 主要内容 | 其他角色参与什么 |
| --- | --- | --- | --- |
| [产品开发需求](产品开发需求模板.md) | 产品；设计补充稿件和交互 | 背景、范围、业务流程、规则、状态、交互、多端共同要求及业务验收标准 | 开发核对现状和可行性；测试检查遗漏、边界和预期是否明确；产品或业务决策人确认业务结果 |
| [技术方案](技术方案模板.md) | 各端开发；后端负责接口和服务端部分 | 当前实现、调用链、接口约定、各端实现、兼容和验证安排 | 产品确认影响业务或交互的变化；测试核对环境和可验证性 |
| [开发任务](开发任务模板.md) | 开发负责人组织，各端开发分别维护 | 任务拆分、负责人、依赖、完成判据和交付进度 | 产品确认范围与优先级变化；测试补充提测及验证依赖 |
| [AI 测试用例](AI测试用例模板.md) | 测试负责人；AI 辅助编写和执行 | 测试数据、工具入口、操作、可判断的检查条件、执行证据及未覆盖范围 | 开发或自动化负责人提供运行能力；产品澄清业务预期；测试负责人审核结果 |
| [人工测试验收](人工测试验收模板.md) | 测试人员与测试负责人 | 账号和数据准备、操作步骤、预期、多端执行记录、缺陷与测试结论 | 开发提供构建及复测条件；产品确认业务与交互是否达到目标 |

### 产品需求内部怎么分工

产品主责维护整份产品需求，其他角色参与确认相关部分，无需让产品填写技术实现。

| 产品需求章节 | 主要填写人 | 协作范围 |
| --- | --- | --- |
| 1 基本信息与确认范围 | 产品 | 各负责人核对自己的信息和确认范围 |
| 2 背景目标与范围 | 产品 | 开发补充有依据的现状；测试补充受影响场景 |
| 3 来源与设计资料 | 产品、设计 | 各自维护原始材料与稿件版本 |
| 4 用户角色与业务流程 | 产品 | 设计补充流程和交互；开发、测试参与澄清 |
| 5 逐条业务与交互需求 | 产品、设计 | 开发反馈平台约束；测试检查边界与异常 |
| 6 多端共同要求与允许差异 | 产品、设计 | 各端开发说明实际约束，由产品确认目标表现 |
| 7 业务验收标准与业务约束 | 产品 | 测试协助写成可判断的结果；开发检查可实现性 |
| 8 待确认问题与业务决定 | 产品协调，对应责任人决定 | 业务和交互问题由产品、业务或设计确认；技术问题转技术方案 |
| 9 需求变更与配套文档 | 产品 | 开发、测试更新受影响的方案、任务和两份测试资料 |

如果某个角色由同一人兼任，仍分别记录业务决定、技术决定和测试结果的责任，不要求增加人员。

## 2 文档写作要求

生成的正式文档要准确、自然、易读，能让产品、开发和测试理解同一件事。

- 写清具体场景、条件、操作和结果；只保留帮助理解或执行的细节，避免空泛表述和机械重复。
- 业务名称、页面名称、字段、状态和技术术语沿用材料及项目中的实际名称，前后一致，不为了显得专业创造新说法。
- 事实有来源，推断和建议明确标注，未知项写入待确认问题。接口、数值、限制、业务规则和执行结果没有依据时不补造。
- 必须使用缩写或技术词时，在首次出现处用简短解释说明。产品需求使用业务语言，工程细节写入技术方案。
- 正文使用自然段；相同维度的比较用表格，操作顺序用编号。不要把所有说明都写成标签堆叠，也不要重复复制同一规则。
- 模板中的填写提示、占位符和无关示例在正式交付前清理；章节按功能裁剪。仍未确定的内容明确列出，不用套话填满。
- 交付前检查术语、版本、编号、文案和预期是否一致，检查语句是否顺畅，确认描述没有超出材料能够支持的范围。

例如，可以写“登录过期时进入登录页；登录成功后返回消息列表，由用户重新点击消息”，并关联来源和需求编号，让开发与测试都能判断目标行为。

### 范围控制与现状核对

先明确本次目标、涉及入口、适用端、本期包含、不包含和必须保留的已有行为。模板按实际功能裁剪，列举的异常、指标和约束只用于检查是否相关，不自动成为本期需求。技术方案、任务和测试也围绕已确认目标及必要影响范围展开。

现状优先从目标业务项目本次适用的各端仓库了解，按各端规范只读追踪受影响的入口、校验、状态、模型、接口和输出。技术方案保留仓库、分支、提交和代码位置，产品需求概括可确认的业务现状。单端代码不直接成为多端目标，客户端代码不能证明完整后端规则或线上表现；未找到实现时记录搜索范围和证据不足。

代码无法确认、材料冲突或涉及业务取舍时，请用户补充确认，说明已有依据、具体影响和最少需要回答的问题。已确认事实、待确认事项和改进建议分别记录。范围外建议不自动转为本期需求、任务或验收条件；确需改变业务范围时先说明原因并由用户确认，其他独立且明确的工作继续推进。

识别到多端业务逻辑或交互不一致且无法判断目标时，及时向用户说明，不等全部文档完成。按同一场景简述本次适用的各端表现、影响和待确认点，在产品需求第 6 节记录；详细依据放在技术方案，并关联同一问题编号。尚未核实的端明确标注，不选某一端或多数端作为默认标准。用户确认后保留决定与日期，更新共同要求及受影响文档；已有明确确认的平台差异不重复询问。

## 3 版本文件夹组织

```text
projects/<项目标识>/prd/
├── README.md                 版本目录索引
└── prd-vxxx-YYYYMMDD/
    ├── README.md             各负责人目录索引
    └── sanshi/               sanshi 负责的需求与文档
        ├── 00-文档索引.md
        ├── 01-产品需求.md
        ├── 02-技术方案.md
        ├── 03-开发任务.md
        ├── 04-AI测试用例.md
        ├── 05-人工测试验收.md
        └── sources/          按需保存本次相关材料
```

其他负责人使用已确认的姓名目录，与 `sanshi/` 同级。个人目录只放本人负责的文档，五种模板按实际需要使用，不要求每个人集齐全部类型或讨论同一版本的所有需求。姓名目录表示文档归属，不改变产品、开发和测试的填写与确认职责。

同一人负责多个需求时，可以在姓名目录下按需求分子目录，按实际范围裁剪章节和篇幅。不得为了补齐整版资料而顺带生成或改写其他人的文档。

日期取版本目录首次创建日，同一版本后续始终复用原目录，不因负责人或日期不同重复创建。在目标项目的 `projects/<项目标识>/prd/README.md` 登记版本入口，版本目录的 README 索引各负责人目录；个人的 `00-文档索引.md` 记录本人负责需求、文档链接、版本和变更同步情况。没有实际版本时不创建假定版本目录。

同一需求涉及不同负责人时，各自维护本人负责的文档，引用相关文档链接、REQ、AC 及已确认版本，跨目录引用时注明负责人。共同业务逻辑和验收要求保持一致，不各自重写一套规则；发现冲突先请用户确认。实际 App 发布记录在对应项目目录按用户同步的信息分别维护。

## 4 文档之间如何关联

- 项目标识和需求版本共同界定编号范围；跨项目引用注明项目、版本及文档链接，相同局部编号不表示同一需求。
- `REQ-001` 表示一条需求，`AC-001` 表示一项业务验收标准，由产品需求统一维护。
- 开发任务可以使用 `DEV-IOS-001`、`DEV-AND-001`、`DEV-HOS-001` 等编号；AI 用例使用 `AIT-001`，人工用例使用 `HT-001`。
- 每项任务和用例关联对应的 REQ、AC 及需求版本。编号创建后保持稳定，废弃后不再使用。
- 配套文档引用已确认的业务规则，不再分别维护一套预期。技术细节由开发确认，测试数据与执行方法由测试确认。

**产品需求保留业务验收标准，详细测试单独维护。** 例如产品确定“登录成功后回到消息列表”，AI 用例补充工具入口、检查条件与运行证据，人工用例补充测试人员需要的操作步骤和预期表现。

两份测试文档面向不同执行者，可以分工覆盖，不要求每一项都重复运行；每个适用 AC 都应有验证安排。版本索引可使用下面的覆盖对照：

| 需求与验收标准 | 适用端 | AI 用例与覆盖范围 | 人工用例与覆盖范围 | 未覆盖项及处理人 |
| --- | --- | --- | --- | --- |
| REQ-001／AC-001 | <端> | <AIT 编号、方法> | <HT 编号、范围> | <内容或无> |

AI 记录与人工记录分别保存，不能相互自动标记为通过。复用已有证据时说明构建、环境和覆盖范围；测试负责人审核质量结论，产品确认业务验收。

## 5 产出和更新顺序

1. 产品整理原始材料、业务目标和交互，设计补充稿件。开发可以同时核对各端现状，将调用链及差异放入技术方案草稿。
2. 产品、开发和测试共同澄清问题，由对应决策人确认共同业务逻辑、交互、允许差异和 AC。
3. 开发完善各端技术方案并拆分任务；测试可以并行准备两份测试用例，不必等代码写完才开始。
4. 各端按自己的项目约定实现。开发提供构建和自检结果；AI 与测试人员按各自范围执行，记录实际证据。
5. 业务需求变化由产品更新 REQ、AC 和变更记录，开发与测试同步受影响内容。旧结果保留，并判断哪些需要重测。

仍有歧义时只暂缓受影响的行为，独立且已确认的工作可以继续。源代码说明当前实现，不能自动决定需求目标或测试预期。

### 生成四份配套文档

```text
请依据已确认的业务项目、适用端、产品需求及其版本，分别生成技术方案、开发任务、
AI 测试用例、人工测试验收四份文档，使用对应模板。

只生成本次本人负责范围内需要的文档，保存到指定版本的姓名目录，当前默认为 sanshi。
其他负责人维护的同一需求资料通过文档链接、编号和已确认版本关联，
不自动复制或改写其他人的全部文档。共同业务逻辑发生冲突时先向我确认。

各端技术实现按各自项目规范填写。每项任务与用例关联 REQ 和 AC；
不重新定义业务预期，不用当前实现反推预期。两份测试共用同一需求版本，
明确各自覆盖、缺口和交接。没有工具、协议或环境依据时写待确认。

方案、任务和测试围绕已确认目标及必要影响范围生成，不扩展无关功能。
现状优先在目标业务项目本次适用的各端仓库核对，不能从客户端代码推定完整后端规则或线上表现。
发现业务范围或预期需要变化时，请我确认后再同步；其他独立工作继续。
识别到无法确认的多端差异时及时向我提问，并在产品需求简述各端表现；
技术方案保留详细依据，各文档关联同一问题和最终决定。

保持专业、通俗、自然、易读；术语和描述有来源，不杜撰。
用例先标记为未执行，不编造实际结果。本轮只生成文档，不执行代码或测试。
```

## 工具选择

下表根据官方公开资料整理于 2026 年 10 月 20 日。适用场景为选型建议。

| 选择 | 官方提供的能力 | 适合怎样使用 |
| --- | --- | --- |
| [飞书需求文档模板](https://www.feishu.cn/template/software-requirement-documentation-template) | 官方模板中心提供需求文档框架 | 团队已使用飞书时，沿用协作习惯并替换为本项目字段 |
| [Notion PRD 模板](https://www.notion.com/en-gb/templates/product-requirement-doc) | 官方 PRD 模板覆盖产品规格、需求和检查清单 | 已在 Notion 管理产品资料的团队可直接改造模板 |
| [Confluence PRD 模板](https://www.atlassian.com/software/confluence/templates/product-requirements) | 目标、指标、假设、用户故事、设计、问题和范围；可关联 Jira | 已采用 Jira 和 Confluence 的团队沿用现有工作流 |
| [GitHub Spec Kit](https://github.com/github/spec-kit) | 为 AI 编程代理提供规格、规划、任务、实现及完成度核对流程 | 希望系统组织需求到实现的团队，可选一个功能试用 |
| [OpenSpec](https://github.com/Fission-AI/OpenSpec/blob/main/docs/overview.md) | 按变更维护提案、规格增量、设计和任务，归档后更新规格 | 现有项目持续迭代，需要明确每次修改哪些行为时可优先评估 |

协作平台承载文档和讨论，Spec Kit 或 OpenSpec 组织开发过程，两类工具可以组合。先确定团队可持续维护的模板；流程工具试用时选其一，观察是否减少澄清和返工。
