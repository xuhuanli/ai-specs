## 5 V538-REQ-003 AI 随访埋点补齐

本项围绕同一笔药方订单建立两条连续业务路径：计划生成后，医生查看与使用，触达患者，患者打开、填写并有效提交；形成反馈后，通知医生，医生实际查看反馈并使用随访小结。客服回访不限定只能发生在患者未反馈时，符合现有业务条件的阶段均可能由医生选择。[SRC-002](https://alidocs.dingtalk.com/i/nodes/YMyQA2dXW79x67bjcdQEl09oJzlwrZgb)

### 5.1 必须区分的统计含义

- 渠道发送成功表示渠道执行结果；患者实际打开反馈单才算有效触达。
- 进入外层消息或分享页，不等于打开反馈单。
- 首次真实作答才算开始填写；是否形成有效反馈，以服务端成功提交的业务结果为准。
- 通知发出、通知点击、反馈详情加载展示是不同事件。聚合通知进入已反馈列表，不等于查看某笔订单的反馈。
- 同一订单可多次打开反馈单，打开记录逐次保留；首次作答按该轮该份反馈单计一次；同轮随访仅形成一份有效反馈。
- 医生自主从开方记录进入并查看反馈，也要计入实际查看。

### 5.2 采集内容

业务记录优先复用已有服务端事实或结构化诊后日志，缺少的信息再补充；行为埋点记录真实用户操作。下表保留原文内容和编号便于追溯，不表示本人鸿蒙仍逐项独立采集。本人采用的四项及 E05/E06 合并结果见第5.3节，建议事件名及原文技术字段保留在来源索引中。

| 原文编号 | 观察内容 | 判定或采集边界 |
| --- | --- | --- |
| B01 | 订单关联的随访配置 | 落单后确定最终开关、提醒日期、是否改动默认配置，相关时间发生后补齐 |
| B02 | AI 随访计划生成结果 | 生成完成，区分成功、失败和回退及原因，记录反馈单版本可用情况 |
| E01 | 医生实际查看随访计划 | 随访重点及反馈单内容已经加载并展示，看到入口不算 |
| B03 | 提醒时间调整 | 医生确认且成功保存新提醒时间 |
| E02 | 医生微信分享 | 原文同时出现“发起分享”和“分享成功”的表述，最终触发口径待确认，不可按送达患者统计 |
| B04 | 反馈单消息发送 | 每次实际发送与结果；区分短信、公众号、咨询 IM 卡片及医生分享相关卡片 |
| E03 | 患者打开反馈单 | 实际打开，保留每次打开、反馈单版本及可识别来源 |
| E04 | 患者首次作答 | 首次真实勾选、输入或上传，不因修改答案重复计数 |
| B05 | 有效反馈形成 | 患者成功提交，或客服按已有业务规则形成有效反馈 |
| B06 | 医生反馈通知发送 | 各通知渠道的发送及结果；聚合通知保留关联范围 |
| E05 | 医生点击反馈通知 | 点击相关待办、咨询卡片或 App Push 并触发跳转 |
| E06 | 医生实际查看反馈 | 具体订单的反馈正文或随访小结加载成功，是医生基础消费的核心判定点 |
| E07 | 医生复制随访小结 | 以能够确认的成功执行为准 |

订单级记录要能关联同一笔药方订单，并区分医生端与患者端行为。渠道无法识别时标为未知，不用最近一次发送强行推断来源。最终事件名称、必填信息、各端与服务端职责、已有埋点复用及去重方案，在详细方案中确认。

### 6.2 V538-REQ-005 已完成随访待办跳转

主需求右侧示例为“助手已完成对患者发送的回访，点击查看回访报告”。点击该条待办后，目标调整为进入对应开方详情页，并拉起对应随访详情弹窗。
