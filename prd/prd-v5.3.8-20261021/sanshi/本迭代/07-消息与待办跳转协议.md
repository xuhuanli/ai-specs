# 鸿蒙消息与待办进入订单后查看反馈

文档v0.2，2026-10-26，关联产品需求v1.4的SAN-REQ-003。消息与待办业务方案均已由用户确认，本轮仅更新需求、方案和测试安排，未修改代码或运行验证。v0.1的待办新增open_reply建议已取消，以下为最终方案。

## 1 消息：RECIPEL按open_reply控制

药方详情Push沿用`RECIPEL`类型，新增`open_reply`。点击后先进入对应订单详情；仅当字段存在且等于`1`时，详情加载成功后自动调用现有“查看反馈”按钮的业务逻辑，打开完整反馈；字段缺失或不为`1`时只进入详情。关闭完整反馈回到同一订单详情。

后台消息原始样例中的字段层级、数字或字符串类型在接入时核对，属于实施材料，不再作为业务方案待决。当前确认入口为药方详情Push，消息中心列表不自动扩围，`FOLLOW_UP`原有独立逻辑保留。Push来源保持“系统通知”。

## 2 待办：命中prescribe/feedback直接查看反馈

首页待办或待办列表触发`igancao://prescribe/feedback`时，使用已有协议参数中的订单号先进入对应订单详情。详情加载成功后自动调用现有`openCompleteFeedback()`，即“查看反馈”按钮的业务方法。不要求新增`open_reply`、反馈流水号或任何控制参数；是否触发由该待办协议本身决定，不受额外开关控制。

后台继续沿用已有`btn_jmp`、订单号及编码方式，不需要为本需求变更待办参数。以下仅示意现有?in=编码JSON形式，订单号为样例；现有#编码JSON和末尾斜杠兼容继续保留。

```javascript
const params = { orderid: "ORDER_ID_EXAMPLE" };
const btn_jmp = "igancao://prescribe/feedback?in="
  + encodeURIComponent(JSON.stringify(params));
```

该链接没有open_reply，也应在进入详情后自动调用查看反馈。其他待办协议及普通订单入口不因此增加自动动作。待办点击标记、完成和列表更新沿用原规则，来源保持“待办”。

## 3 共同执行及异常边界

两种入口只在触发条件上不同，详情端共用一次性自动查看反馈处理。客户端可以内部生成并透传动作意图；这不属于后台新增待办参数。待办应在原始协议仍可区分时生成意图，避免归一化到共用订单详情路由后误影响其他入口。

详情请求成功且当前订单数据绑定完成后，消费本次意图并调用现有查看反馈业务方法，不模拟UI点击，不复制一套反馈定位逻辑。复用现有方法从订单响应取得`recipel.invest_serial`、订单及患者上下文；缺少反馈流水号等情况沿用该方法原校验与提示，保留订单详情，不打开错误反馈。本期不增加通知指定历史反馈的协议或额外反馈标识。

协议无法解析、订单号缺失和详情加载失败分别沿用原错误处理，不自动打开反馈。同一次入口点击只自动调用一次，关闭反馈、刷新或从反馈返回均不重复；异步返回需确认页面仍有效且订单未切换。新埋点API继续后置，不作为导航前置依赖。
