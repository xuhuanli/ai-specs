## 1 需求与边界

只要开方页面实际回填了某个订单的数据，后续调用 `appapi/ai_summary/complete_text_task` 时，就必须用 `origin_orderid` 携带该来源订单号。是否需要携带取决于数据来源，不限制从哪个页面跳转进入，也不以是否点击“复诊开方”或复诊标记为判断条件。主诉、诊断、图片等任一订单数据回填均属于本需求。

本次承接前序鸿蒙分析，实施方案仅覆盖鸿蒙；不推定 iOS／Android 已符合或同步授权修改。业务规则可作为后续其他端对齐依据。本需求归入现有 V5.3.8，计划排期保持原记录。

| 场景 | 目标行为 |
| --- | --- |
| 任意入口进入开方，成功回填订单 A 的数据 | 本次开方后续创建图文 AI 任务时传 `origin_orderid=A` |
| 开方页自动生成、手动生成 AI 推荐，包括编辑药材页共用推荐入口 | 使用同一来源订单号，不按自动／手动或入口区分 |
| 开方页 → AI 写病历 → 读文识图提交 | 将来源订单号透传到图文页，并随同一接口提交 |
| 保存包含订单回填数据的草稿，再从草稿箱或患者入口恢复 | 恢复对应来源，后续调用继续携带；不能借用新入口的订单号覆盖草稿来源 |
| 订单回填后，医生编辑主诉、诊断或图片 | 推荐保留来源，编辑不改变这次开方所基于的订单 |
| 仅携带跳转订单号，但查询失败、剂型不支持或未实际回填 | 推荐不据跳转参数建立新来源，不把该订单号当作已回填订单 |
| 新建开方或 AI 引用新建开方，未使用订单数据 | 推荐不传该字段，不自动查询历史订单来补关联 |

参数名和适用条件来自用户本次说明；无来源省略字段、来源生命周期和草稿兼容策略已随本方案由用户确认，作为实施基线。字段为请求顶层参数，按订单号字符串传递，不放入 `std_summary`，不转换为数字。代码现有 API 使用相对路径 `ai_summary/complete_text_task`；沿用网络层地址配置，不拼接第二层 `appapi`。

## 3 已确认实现

### 3.1 在数据回填处记录来源

在页面持有的 `PatientModel` 增加独立字符串字段 `originOrderId`，初始为空，表示当前开方实际使用的来源订单。它与患者、病历、图片处于同一页面生命周期，不使用全局单例或跨患者缓存。

在普通开方共用的订单回填链路登记：订单响应有效、剂型可接受且本次数据确实被应用后，优先采用响应 `recipel.pay_orderid`；缺少时使用本次成功查询所用的 `orderid`。订单号保持字符串。在患者、药方回填完成的通知以及 AI 稳定窗口启动之前写入，保证由本次回填触发的 AI 创建读取同一来源。请求失败、未接受数据时不写入新的来源；若页面仍保留先前已接受的数据，其来源也保持一致。

不通过 `recipeSourceType`、`followUpVisit`、`isChangeOrder` 或页面名称筛选。不在各跳转入口重复添加判定，也不单凭路由存在订单号就提前认定回填成功。医生编辑本次开方内容、进入预览再返回或在原页面引用 AI 内容时保留来源；新的开方实例默认清空，有新的订单数据被接受时与数据一并更新。

### 3.2 两条请求链分别接入同一来源

1. 推荐任务：在 `AIPrescriptionRuleService.buildCreateTextTaskParams()` 中读取 `patientModel.originOrderId`；非空时追加顶层 `origin_orderid`。自动、手动及编辑药材共用入口自然覆盖，保留既有创建条件及所有原参数。
2. AI 写病历图文：`MakePrescribePatientInfo.buildAiRecordInputParams()` 将同一来源作为可选参数透传；在 `AIAssistantImageTextRouteParams`、状态和解析中接收，再由 `buildSubmitParams()` 非空追加 `origin_orderid`。独立 AI 图文入口没有来源时维持原行为；保留 `old_task_id` 等原参数，不把 AI 任务 ID 当作订单号。

### 3.3 保留草稿来源

本地草稿另存顶层 `origin_orderid`，从专用来源字段读取；只在草稿参数副本上添加，不修改真实开方提交和预览协议。初始草稿快照与保存时采用一致的来源字段规则，避免未编辑页面被误判为草稿变化。

恢复时优先使用草稿的 `origin_orderid`；对缺少此字段的旧草稿，兼容读取其已有 `orderid_origin`。恢复患者信息及通知 UI 前写入。两者均缺少时保持空值，不根据当前入口订单号、患者最新订单或 AI 任务 ID 猜测。旧草稿来源本来就未保存时，客户端无法可靠还原，需在测试中明确该边界；不为此额外拉历史订单并覆盖草稿。

### 3.4 方案比较

| 做法 | 评估 |
| --- | --- |
| 仅给“复诊开方”入口传订单号 | 无法满足不限入口，也漏普通选患者、草稿及 AI 写病历图文链路 |
| 在请求时直接读路由／复诊标记／现有 `pay_orderid` | 路由不证明回填成功，复诊标记不覆盖所有入口，现有草稿恢复又未恢复患者模型的订单号；难以稳定表达实际数据来源 |
| 共用回填点记录专用来源，两条请求组装处消费，草稿延续 | 推荐。来源与实际数据绑定，覆盖入口无需枚举；改动集中在现有模型、回填、参数和草稿链路，不新增网络请求、全局上下文或跨模块反向依赖 |
