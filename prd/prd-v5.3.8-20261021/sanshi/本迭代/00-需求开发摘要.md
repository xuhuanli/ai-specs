# V5.3.8 sanshi 本迭代需求开发摘要

sanshi 本迭代只负责 Android 预览处方 UI、鸿蒙预览处方入口与新页面，以及鸿蒙 AI 随访待办跳转、埋点补齐和两类随访弹窗 UI 调整。其他整版需求不纳入本人开发范围。

本摘要及产品需求、技术方案、任务更新为 v1.2，2026-10-22。新增随访顶部平铺与小结复制，四项埋点及参数已逐项确认，埋点继续等待新增 API。Android 与鸿蒙预览的既有实施、测试及提交状态见[开发任务](03-开发任务.md)；本轮只更新随访文档，未实施新增 UI 或埋点。

## 2 预览处方的确认结果

最新已读设计为 [UI 页面更新中的预览处方](https://www.figma.com/design/aFKpQlzeW8NibL23OpY5lq?node-id=20638-18676)。画板名仍为“待付款”，实际页面标题是“预览处方”，不能据画板名引入待付款状态。

设计包含顶部标题与背景、患者信息、药方信息、诊后随访与咨询、医师责任险、合计与明细，以及底部生成按钮。示例数值、患者资料和药材不是固定规则；各剂型和条件字段保留实际业务语义。

| 审核关注项 | 本次确认或待补内容 |
| --- | --- |
| Android 原内容 | 原有患者信息、附件、剂型差异、药材、费用及优惠、隐藏金额明细配置和发送回调均需保留 |
| 鸿蒙数据 | 根据当前开方信息和预览计算结果组装；复用订单详情外观，不直接执行订单详情的查询和状态解析 |

## 3 随访 UI 与四项 APP 埋点

两页顶部重点／小结取消展开收起，完整反馈新增小结复制，三个复制区域都计消费。此前“不新增小结复制”的限制已由2026-10-22用户确认替代。

| 事件标识符 | APP 上报位置 | 参数数量 |
| --- | --- | --- |
| followup_plan_view | 入口传入页面来源，在随访计划弹窗内，全部内容加载成功并实际展示后统一上报。仅点击按钮、加载中或加载失败不计。 | 4 |
| followup_wechat_share_initiate | 统一在分享处理链路中确认微信调用成功且已执行跳转微信后上报。点击按钮、版本同步成功或普通函数返回均不能替代该结果。 | 3 |
| followup_feedback_view | 各入口沿本次链路传来源，仅在最终完整反馈弹窗内，反馈正文／随访小结加载成功并实际展示后上报。入口和中间页面不另计。 | 5 |
| followup_summary_copy | 三个复制区域都使用本事件；在剪贴板写入成功后上报。新增小结复制成功后提示“复制成功”，保留既有两类复制内容。 | 3 |

计划查看来源只区分开方记录、开方详情；反馈查看区分系统通知、消息、待办、咨询、开方页、开方记录、开方详情。引导链路保留原来源，三个手动入口分别记录。查看按打开周期计数，分享和三个区域的复制按每次成功操作计数。

后台自行处理的四个标识符为 `followup_order_config`、`followup_order_create`、`followup_remind_time_change`、`followup_form_msg_send`，APP不开发，单列供用户找后台确认；患者端已从本次清单移除。完整位置、15项参数、来源与待补协议见[APP埋点清单](06-APP埋点清单.md)和[表格](06-APP埋点清单.xlsx)。

## 4 已核对的实现依据

Android 存在 `PrescribePreviewFragment`，由开方页的预览动作进入，使用当前缓存与 `TransferPreviewData`。订单详情已有 V2 患者、药方、诊后设置和费用布局可供复用。鸿蒙普通开方页的预览按钮被注释，订单详情有可复用药方组件，患者和账单区需适当拆分。

鸿蒙待办列表与首页待办共用 `todoItemJump` 协议入口；普通消息 `FOLLOW_UP` 是另一条路径。已有订单详情支持按特定路由参数加载后打开其他视图，但本期的随访参数和目标仍需单独确认。现有 AI 行为上报已通过后台 GAPI 封装；该历史接口不能直接认定为本期随访接口。

订单模块已接入动态页面加载，开方模块也已有动态进入该模块页面的调用。鸿蒙预览页按用户确认在订单模块内复用，无需为本次预览整体下沉展示组件。代码位置、分支快照及方案见[技术方案](02-技术方案.md)，不把静态代码核对表述为运行验证。
