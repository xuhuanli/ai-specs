# V5.3.8 sanshi 本迭代需求开发摘要

sanshi 本迭代只负责 Android 预览处方 UI、鸿蒙预览处方入口与新页面，以及鸿蒙 AI 随访待办跳转和埋点补齐。其他整版需求不纳入本人开发范围。

本摘要与配套文档版本为 v1.1，更新日期为 2026-10-21；业务规则与排期已确认。用户已授权先实施 Android 预览 UI，当前代码已实现、编译通过，待页面验收及用户确认提交；本轮未实施其他功能。鸿蒙预览及随访已确认规则保持不变，埋点采用后台新增 API 并后置开发。

## 2 预览处方的确认结果

最新已读设计为 [UI 页面更新中的预览处方](https://www.figma.com/design/aFKpQlzeW8NibL23OpY5lq?node-id=20638-18676)。画板名仍为“待付款”，实际页面标题是“预览处方”，不能据画板名引入待付款状态。

设计包含顶部标题与背景、患者信息、药方信息、诊后随访与咨询、医师责任险、合计与明细，以及底部生成按钮。示例数值、患者资料和药材不是固定规则；各剂型和条件字段保留实际业务语义。

| 审核关注项 | 本次确认或待补内容 |
| --- | --- |
| Android 原内容 | 原有患者信息、附件、剂型差异、药材、费用及优惠、隐藏金额明细配置和发送回调均需保留 |
| 鸿蒙数据 | 根据当前开方信息和预览计算结果组装；复用订单详情外观，不直接执行订单详情的查询和状态解析 |
| 顶部与底部 | 鸿蒙顶部固定“预览处方”；底部仅一个生成按钮，不展示订单详情的多个业务操作 |
| 医助角色 | 用户已确认保留原角色规则；普通医生显示“生成处方并发送给患者”，受限医助沿用给医生审核的文案与流程 |
| 药方编号 | 仅开方成功后才有编号；Android、鸿蒙预览均隐藏编号行和复制入口，不显示占位编号，也不为预览申请或查询编号 |
| 医师责任险 | 两端按现有订单详情逻辑展示，复用固定文案“医师责任险”“甘草医生已为您投保”、样式和条款链接；不新增保险状态字段或接口 |
| 鸿蒙模块方案 | 订单模块内新增独立预览页并共用适用展示；开方模块通过公共动态路由传入当前预览数据，生成操作回传后沿用原开方流程 |
| 风险提示与签名 | 鸿蒙对齐 Android，在进入预览前完成适用的风险确认及签名；正式生成继续原提交检查，不重复同一次已确认内容 |
| 返回与生成 | 对齐 Android：点击生成不立即关闭预览，取消确认或提交失败保留预览，需要修改时返回编辑；成功后清理预览并完成原成功导航。主动返回保留开方数据 |
| 鸿蒙费用明细 | 按当前设计与鸿蒙订单详情展示，不额外引入 Android 的隐藏金额明细配置判断；金额与明细绑定本次预览响应 |
| 参数差异备注 | `usage_time`、`is_special_writing`、`auxiliaryNotify` 见 SAN-NOTE-001；开发涉及时找用户确认，再更新逻辑及文档，暂不自动补传，不阻塞方案确认 |

查看按一次打开成功展示记一次，刷新重建不重复、关闭重开成功再计；分享和复制按每次真实成功操作记录，同一次操作的重复回调不多计。E07 只保留原文追踪编号，不新增随访小结复制按钮。

原文 B01 至 B06 优先由后台记录，E03、E04 属于患者端，均不分配到本人四项鸿蒙行为埋点。详细验收与待确认问题见[产品需求第6至8节](01-产品需求.md)。

## 4 已核对的实现依据

Android 存在 `PrescribePreviewFragment`，由开方页的预览动作进入，使用当前缓存与 `TransferPreviewData`。订单详情已有 V2 患者、药方、诊后设置和费用布局可供复用。鸿蒙普通开方页的预览按钮被注释，订单详情有可复用药方组件，患者和账单区需适当拆分。

鸿蒙待办列表与首页待办共用 `todoItemJump` 协议入口；普通消息 `FOLLOW_UP` 是另一条路径。已有订单详情支持按特定路由参数加载后打开其他视图，但本期的随访参数和目标仍需单独确认。现有 AI 行为上报已通过后台 GAPI 封装；该历史接口不能直接认定为本期随访接口。

订单模块已接入动态页面加载，开方模块也已有动态进入该模块页面的调用。鸿蒙预览页按用户确认在订单模块内复用，无需为本次预览整体下沉展示组件。代码位置、分支快照及方案见[技术方案](02-技术方案.md)，不把静态代码核对表述为运行验证。
