# 多项目多端协作工作区

本工作区用于组织不同部门、不同业务项目的多端同步开发。每个业务项目在 `projects/<项目标识>/` 下维护自己的需求、跨端说明和发布记录；各端代码放在项目的 `repos/` 下，分别保留独立 Git 仓库。

工作区根目录的 Git 仓库统一记录公共资料和各项目协作文档的本地历史，排除各端代码。不将代码仓库作为子模块、gitlink 或普通目录提交。公共资料和项目协作文档仅本地维护，不上传远程。

## 任务与规范边界

开始任务先确定业务项目，再确定需求版本、本人负责范围、适用端和目标代码仓库。目标项目明确时直接进入，不扫描其他项目；信息有歧义且会影响操作时再确认。

1. 根目录 [AGENTS.md](AGENTS.md) 定义通用流程、文档写作和 Git 授权边界。
2. `projects/<项目标识>/AGENTS.md` 与 README 定义本项目的业务范围、跨端协作、资料和仓库入口。
3. 各端代码仓库及目标目录的 AGENTS、README 和项目规范定义该端的架构、实现、分支、提交及验证方式。

同一项目内按需求适用端确认共同业务流程、规则、状态含义和验收口径；已确认的平台差异保留。两个端的项目按两个端处理，新增平台确认接入后再纳入相关需求。不把另一个业务项目的规则、版本、账号、接口或历史决定作为默认依据。

## 需求与共用模板

正式版本资料存放在 `projects/<项目标识>/prd/prd-vxxx-YYYYMMDD/<姓名>/`。日期取该项目该版本目录首次创建日；同一版本后续复用原目录。当前用户目录名为 `sanshi`，只维护本人负责范围，不自动生成整版需求或其他人的资料。

各项目分别在自己的 `prd/README.md` 登记版本，版本内 README 索引负责人目录。需求、方案、开发任务、AI 测试用例和人工验收关联同一项目、版本及 REQ、AC 编号；跨项目引用必须注明项目和来源。不同项目的相同版本号、局部编号不表示同一需求。

公共模板在 [docs/requirements/](docs/requirements/README.md)，生成文档按目标项目实际端裁剪。项目内长期约定写入项目 README 或项目专题文档；跨项目通用方法在根目录维护。

## 发布记录

发布记录分别放在各项目目录，按实际接入的端维护。云诊室现有三份发布记录的格式、内容和历史日期口径继续保留，见[云诊室项目说明](projects/yzs-doctor/README.md)。CRM 在收到已确认的端、版本、发布日期和发布内容后再建立对应记录。

各端独立确认发布事实，不从计划、代码分支、标签或另一端记录推定已发布。

## Git 与迁移说明

- 根文档仓库统一记录公共资料和项目文档，仅做本地提交，不执行 push；各项目目录不另建文档 Git 仓库。
- 根仓库当前已有名为 `origin` 的远端配置，本次迁移保留既有配置，不连接或使用该远端，不将其作为文档上传授权。后续不新增文档远端；如需调整已有配置，单独按明确指令处理。
- 各项目 `repos/` 中的代码仓库由根 `.gitignore` 排除，只有接入说明 `repos/README.md` 纳入文档历史。代码的 commit、push、amend 依用户明确授权及所属仓库规范执行。
- Git 操作明确目标目录；根文档的本地提交与各端代码提交分别处理，分别报告状态。
- 2026-11-02，原根目录的云诊室需求、项目说明、发布记录和三个代码仓库迁入 `projects/yzs-doctor/`。通用模板保留在根 `docs/requirements/`，原 Git 历史保留。
- 三个代码仓库的新位置为 `projects/yzs-doctor/repos/` 下同名目录。后续在新位置打开工程；本地 IDE、构建缓存和外部脚本若保存旧绝对路径，需按新位置重新打开、同步或更新。
- 历史验证日志、JSON 证据及原始材料保留当时的路径和执行事实；维护文档的当前链接与可复用脚本已按新目录调整。历史记录不代表迁移后重新执行了业务验证。
